# Architecture

## Layout

```
WowLauncher/
  Models/          Wire formats and state, described below
  Services/        Download, verification, update, game launch
  ViewModels/      MVVM view models
  Views/           Avalonia AXAML
  Controls/        Custom controls
  Localization/    Language catalogues
  Assets/          Fonts, backgrounds, icons
WowLauncher.Tests/ xUnit tests
deploy/            Packaging, publishing, manifest tooling
```

## The two manifests

Everything the launcher downloads is described by JSON served from the download
host. There are two different shapes, and mixing them up is the most common
source of bugs in this codebase.

### Server manifest: ServerManifest

One document per product, served as `manifest.json`. It answers the question
"what should the player have installed right now".

| Field | Meaning |
|---|---|
| `product`, `current_version`, `build_date` | identity of the release |
| `active_phase` | which progression phase is live. The launcher resolves the required client build from it |
| `base` | the whole client archive: url, size, sha256 |
| `patches[]` | incremental patches on top of `base` |
| `phases[].clients[]` | per phase client builds, one entry per operating system: `windows`, `linux`, `macos` |
| `launcher` | Windows launcher build for self update |
| `launcher_linux` | Linux launcher build. A separate top level field, never nested under `launcher`, so the Windows path stays untouched |

An absent optional field means "not published yet" and has to be handled as a
no-op, never as an error. The operator publishes partial manifests routinely. A
launcher that throws on a missing field breaks every player at once.

### Client file manifest: ClientFileManifest

Optional, referenced from the server manifest. Lists every file inside the
client tree with size and sha256, so a damaged install can be repaired file by
file instead of downloading a multi gigabyte archive again. Generated by
`deploy/make-file-manifest.sh` from an extracted client tree. Paths always use
`/` as the separator, no matter which operating system generated the manifest.

When it is absent, every consumer falls back to the whole archive path.

## Download and verification

1. Read the server manifest
2. Resolve the client for the active phase and the current operating system
3. Download with resume support
4. Verify SHA256 against the manifest before extracting
5. Extract, then optionally verify per file against the client file manifest

A download is not trusted because it completed. It is trusted because its
checksum matches a value that was published separately.

## Self update

The launcher compares its own version against `launcher` on Windows or
`launcher_linux` on Linux and offers an update. Updates are check and notify
only until artifact signing is wired into the release pipeline.

macOS has no launcher field yet. See the open issues.
